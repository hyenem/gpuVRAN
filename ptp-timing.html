PTP 동기 & 프론트홀 타이밍

"GPS·PTP로 시간을 맞춰 CPU에서 읽고, 그걸 다른 모듈들에 뿌린다." — 이 구조가 GPU vRAN으로 가면 어떻게 바뀌는지가 이 페이지의 핵심입니다. 결론부터: 시간의 진실원이 CPU 시스템 시계에서 NIC 하드웨어 시계(PHC)로 내려갑니다.

1. 큰 그림 — 두 시계 도메인

vRAN 타이밍을 이해하는 멘탈 모델은 단 하나 — 두 개의 시간축이 있고, 그 둘을 정렬하는 게 전부라는 것입니다.

  • 망 시간 (절대 시각) — GPS/PTP에 동기된 TAI. "지금 air interface가 몇 번 슬롯인가." NIC/DPU의 PHC(PTP Hardware Clock)가 관리.
  • 처리 시간 (상대) — GPU 파이프라인이 도는 시간. "이 연산이 마감 전에 끝나는가." 슬롯/심볼 인덱스 공간에서 동작.

이 둘을 잇는 다리가 "PHC 절대시각 ↔ 슬롯 번호(SFN) 앵커링" 한 줄입니다. 이 페이지의 모든 내용이 결국 이 다리를 어떻게 놓느냐로 수렴합니다.

📐 S-plane이란

O-RAN 프론트홀은 4개 평면으로 나뉩니다 — U(사용자 데이터), C(제어), S(동기/Sync), M(관리). 이 페이지의 1·2절은 S-plane(시간 동기)과 U/C-plane의 전송 타이밍을 다룹니다.

시간 흐름 구조도

GPS/PTP에서 출발한 시간이 NIC PHC(단일 진실원)로 모인 뒤, 세 갈래 — 제어 평면(SW), 수신(RX), 송신(TX) — 으로 분배되는 전체 그림입니다.

그림 — vRAN 시간 흐름: GPS/PTP → NIC PHC(진실원) → 제어(SW)·RX·TX 분배

세 개의 시계 — GPU 시간 ≠ CPU 시간

구조도에서 자주 나오는 질문: "제어 평면(SW)은 CPU인데, 그럼 GPU가 쓰는 시간과 CPU 시간은 같나?" 답은 — 시계가 사실 3개 있고, GPU는 절대 시간을 아예 안 씁니다.

시계동기 상태정체
NIC PHCGPS/PTP에 직접 규율진짜 기준 (절대시각)
CPU 시스템시계phc2sys가 PHC에 맞춤PHC의 사본 (오차 수십 ns~sub-µs)
GPU 내부 타이머❌ 아무것에도 동기 안 됨free-running 카운터 (경과시간 측정용)
  • CPU 시간 ≈ PHC — phc2sys가 맞춰주므로 거의 같음 (servo 오차 + SW 읽기 지터 때문에 "정확히"는 아님).
  • GPU 시간 ≠ CPU/PHC — GPU의 clock64()/globaltimer는 독립 오실레이터라 PTP에 동기 안 되고, 값도 다르며 시간이 가면 drift. GPU엔 "PTP 동기 절대 시계"가 기본 제공되지 않음.
💡 그래서 GPU는 슬롯 인덱스로 우회

GPU 시간과 CPU 시간을 맞추려 하지 않습니다. GPU는 "지금 몇 시"가 아니라 "슬롯 N을 처리하라"만 받고, "언제"(절대시각)는 NIC(PHC + Send Scheduling)나 CPU(PHC 동기 시계)가 책임집니다. 즉 "GPU 시간 == CPU 시간?"이라는 질문 자체가 성립하지 않도록 시간 책임을 GPU 밖으로 빼낸 게 설계의 핵심입니다. (GPU에서 절대 타임스탬프가 필요하면 GPU 타이머↔PHC 오프셋을 측정·주기 재보정해야 하며 drift를 감수해야 합니다.)

2. PTP · GPS 시간 동기 (S-plane)

주제핵심
PTP 프로파일IEEE 1588v2 + ITU-T G.8275.1 (Full Timing Support — 경로의 모든 노드에 Boundary Clock 필요). cf. G.8275.2(부분 지원)
주파수 동기SyncE로 주파수, PTP로 위상/시각 → 하이브리드 모드
클럭 등급G.8273.2 Class C (T-BC, max|TE| = 30 ns) — 5G 프론트홀 목표치. T-GM / T-BC / T-TSC
동기 토폴로지LLS-C1~C4 — DU↔RU 사이 동기 분배 4가지 모델
타이밍 예산셀 위상 동기 ±1.5 µs(GNSS 기준), 안테나 간 상대 TAE는 훨씬 빡빡(수십~수백 ns)
💡 PHC = 진짜 시계

리눅스에서 PTP는 ptp4l(PTP 동기)과 phc2sys(PHC↔시스템시계 정렬)로 돕니다. 여기서 핵심은 — NIC의 PHC가 GPS/PTP에 직접 규율되는 하드웨어 시계이고, CPU 시스템 시계(CLOCK_REALTIME)는 그 PHC를 phc2sys로 따라가는 사본이라는 점입니다. GPU vRAN에선 이 PHC가 시간의 중심이 됩니다.

3. 패킷 타이밍 & 전송 윈도우 (U/C-plane)

프론트홀 패킷(eCPRI over Ethernet)은 정해진 시간 창 안에 도착/출발해야 하고, 어기면 RU가 버립니다. 이게 "타이밍 포함 패킷 송수신"의 실체입니다.

윈도우의미
T1aDL C/U-plane을 공중(air) 슬롯 경계 이전에 보내야 하는 송신 윈도우
Ta3 / Ta4UL 데이터 수신 윈도우 (RU→DU)

GPU vRAN에서 어려운 두 부분

  • RX: NIC이 eCPRI 수신 → GPUDirect로 GPU에 직접 DMA → 각 패킷이 어느 슬롯/심볼인지 알아야 함 → flow steering으로 U/C-plane 분류 + 재정렬.
  • TX: GPU가 IQ 생성 → 정밀한 시각에 송신해야 함(T1a). 소프트웨어로는 µs 정밀도 보장 불가 → NIC 하드웨어가 패킷을 페이싱.
🔧 NVIDIA의 답 — "5T for 5G"

ConnectX-6 Dx/7·BlueField에서 동작하는 타이밍 가속 묶음:

  • Accurate Send Scheduling — "슬롯 시작 타임스탬프 + 오프셋(예: 700 µs)"으로 하드웨어가 정확한 시각에 패킷 송출
  • eCPRI Windowing — SW가 스케줄, HW가 윈도우 내 전송 가속
  • eCPRI flow steering — 들어오는 패킷을 분류해 올바른 큐/GPU로

예제 코드: NVIDIA/5t5g (GitHub) — DPDK 앱에서 슬롯 시각에 패킷을 정확히 쏘는 법을 보여줍니다.

4. 수신 패킷의 시간 정렬 처리 (RX)

TX가 "정확한 시각에 쏘기"였다면, RX는 "제때 도착한 패킷을 올바른 슬롯에 모아 마감 안에 처리하기"입니다. 핵심 반전 — 도착 시각으로 슬롯을 판단하지 않습니다. 패킷 헤더가 자기가 어느 슬롯/심볼인지 직접 알려줍니다.

① 받은 패킷은 자기 정체를 안다

O-RAN U-plane(eCPRI) 패킷에는 헤더가 붙어 있습니다:

  • eAxC ID — 어느 안테나/캐리어 스트림인지
  • frameId / subframeId / slotId / startSymbolId — 어느 프레임·슬롯·심볼인지
  • section (startPrbu, numPrbu) — 어느 주파수 자원(PRB)인지 + 그 뒤 IQ 샘플

거기에 NIC이 찍는 하드웨어 RX 타임스탬프(PHC 시각)가 더해집니다. 그래서 패킷이 순서 뒤바뀌어 와도, 늦게 와도 — 헤더만 보고 "슬롯 N, 심볼 M, PRB k"에 제자리로 꽂으면 됩니다. 도착 순서는 중요하지 않습니다.

② 수신 처리 흐름

RU ──(eCPRI U-plane)──▶ [NIC]
                          │ ⓐ HW 타임스탬프 + flow steering(eAxC ID로 분류)
                          │ ⓑ GPUDirect로 GPU 메모리에 직접 DMA
                          ▼
                  [슬롯/심볼 인덱스 버퍼]  ← ⓒ 헤더대로 제자리에 배치(reorder)
                          │
                          ▼  ⓓ 슬롯 N의 "처리 데드라인"에 트리거
                  [GPU 파이프라인]  FFT→채널추정→등화→디매핑→LDPC

핵심은 ⓒ — 도착하는 대로 슬롯 버퍼의 올바른 위치(offset)에 헤더 기준으로 채워 넣는 것입니다. 쓰는 위치가 곧 정렬이라, 별도 정렬 단계가 없습니다.

③ 언제 GPU를 깨우나 — 두 트리거

방식동작특징
Time-triggeredPHC에서 파생한 타이머가 슬롯 데드라인에 발火 → 처리 시작결정론적 (선호)
Data-triggered"슬롯 N 마지막 심볼 도착" 이벤트로 시작빠르나 늦은 패킷에 취약

실무는 보통 하이브리드 — 데이터로 일찍 시작하되 데드라인 타이머가 안전망. "슬롯 N 패킷은 PHC 시각 T까지 다 와야 한다"는 윈도우(Ta4)를 PHC에서 계산해 두고, 그 시각이 되면 안 온 패킷을 기다리지 않고 처리를 시작합니다.

⚠️ 늦거나 빠진 패킷 — 데드라인이 완결성보다 우선

vRAN 철칙: 기다리면 죽는다. 마감을 넘기면 HARQ 타이밍을 못 맞춰 슬롯 전체가 무효가 됩니다. 그래서 데드라인까지 안 온 패킷은 erasure(소실)로 처리 — 해당 RE를 0/미상으로 두고 진행하며, LDPC·채널코딩이 일정 소실을 복구합니다. "완전한 데이터를 늦게"가 아니라 "불완전해도 제때"가 정답입니다.

④ 처리 자체에 지터가 없게 — 결정론

  • Persistent kernel / CUDA Graphs — 매 슬롯 커널 launch 오버헤드·지터 제거. 커널을 띄워두고 슬롯만 받음.
  • 더블 버퍼링(ping-pong) — 슬롯 N 처리 중 슬롯 N+1 패킷이 다른 버퍼에 쌓임.
  • 고정 예산 — UL 처리는 HARQ 데드라인(n+k 슬롯) 안에 끝나야 하므로 슬롯당 시간(수백 µs)이 고정.

⑤ NIC이 직접 하는가? — 하드웨어/소프트웨어 역할 분담

"NIC이 이걸 다 직접 하나?"의 답은 부분적으로 예입니다. 타이밍·전송 원시기능은 NIC 하드웨어가, 내용 해석·배치·트리거는 소프트웨어(또는 DPU)가 합니다.

기능누가
PHC(PTP 하드웨어 시계), HW 타임스탬프, Boundary ClockNIC HW ✅
Flow steering (eAxC ID로 큐 분류)NIC HW ✅
GPUDirect 직접 DMA (GPU 메모리에 적재)NIC HW ✅
Accurate Send Scheduling (TX 정밀 송신)NIC HW ✅
O-RAN 헤더 파싱 → 슬롯/심볼/PRB 오프셋 배치(reorder)SW(DPDK) 또는 DPU/GPU ⚠️
IQ 압축 해제 (BFP 등)GPU 또는 DPU 가속기 ⚠️
슬롯 데드라인 타이머로 GPU 깨우기SW(CPU 스레드/GPU) ⚠️
신호처리(FFT·LDPC…)GPU

NIC은 "이 패킷을 큐 3번으로" 까진 하지만, "이 IQ를 슬롯 N 심볼 M에 압축 풀어 채워라" 같은 의미 기반 배치는 못 합니다 — 프로그래머블한 주체가 필요하죠. 그 한계를 메우는 게 DPU(BlueField): ConnectX의 HW 오프로드에 Arm 코어 + 가속기를 얹어, ⚠️ 항목 상당수를 호스트 CPU에서 카드 위로 옮깁니다. NVIDIA Aerial은 ConnectX/BlueField + GPU를 이렇게 묶은 것입니다.

5. ★ 시간 배포 구조의 변화 (Before / After)

여기가 당신의 현재 구조와 직결되는 부분입니다. 지금은 CPU 시스템 시계가 단일 진실원이고, 응용이 그걸 읽어 소프트웨어로 각 모듈에 슬롯 타이밍을 뿌립니다.

Before — CPU 중심 SW 배포 (현재)

GPS(PPS+ToD) ──┐
               ├─▶ [CPU 시스템 시계] ──(SW로 읽어서)──▶ 모듈 A, B, C…
PTP grandmaster ┘      ↑ ptp4l/phc2sys              (슬롯 경계를 SW 브로드캐스트)

4G·초기 vRAN에선 문제없습니다. 하지만 SW 경로는 스케줄링·인터럽트로 지터가 µs~ms — 제어용엔 충분해도 프론트홀 U-plane(수십~수백 µs 윈도우)엔 치명적입니다.

After — NIC 하드웨어 앵커 (GPU vRAN)

GPS(PPS) ──┐
           ├─▶ [NIC PHC = 새 진실원] ─┬─▶ (HW 타임스탬프) 수신 eCPRI에 시각 직접 기록 (RX)
PTP ───────┘                          ├─▶ (Accurate Send Scheduling) 정확한 시각에 송출 (TX)
                                      └─▶ phc2sys ─▶ CPU 시스템 시계 (제어·로그·OAM용 유지)
항목Before (CPU 중심)After (GPU vRAN)
PTP/GPS 규율CPU에서 ptp4l/phc2sys동일 (CPU 계속)
진실원 시계CPU 시스템 시계NIC PHC (HW)
제어 모듈 시간 배포SW로 읽어 뿌림그대로 OK
슬롯 타이밍 배포SW 브로드캐스트NIC HW 타임스탬프 + 슬롯 앵커링으로 대체
⚠️ 당신의 케이스 (b) — 슬롯 타이밍 배포 모듈이 1순위 재설계 대상

뿌리는 시간이 제어용 거친 시각이 아니라 무선 프레임 타이밍(슬롯 경계) 그 자체라면, 그 모듈은 그대로 옮길 수 없습니다. GPU vRAN에선 슬롯 경계를 SW로 브로드캐스트하지 않고 —

  • NIC PHC를 공통 시간 앵커로 두고,
  • 각 소비자(GPU 파이프라인, 송신 스케줄러)가 하드웨어 타임스탬프 + PHC↔SFN 매핑에서 슬롯 타이밍을 직접 끌어오게

바꿔야 합니다. 즉 "한 모듈이 시간을 계산해 뿌리는" 푸시(push) 구조에서, "공통 PHC를 기준으로 각자 끌어오는" 풀(pull) 구조로 바뀝니다.

왜 예전엔 중앙에서 뿌렸나 — 그 역할은 어디로?

"기존엔 한 모듈이 시간을 뿌렸는데 이제 각자 가져가라고?" — 중앙 배포엔 분명한 이유가 있었고, 그 이유는 사라지지 않습니다.

  • 단일 규율(servo) 소스 — PTP/GPS 보정 루프는 한 곳에만. 모듈마다 servo 돌리면 제각각 drift.
  • 일관성 — 모두가 같은 값/에폭 참조 → 어긋남 방지.
  • 하드웨어 추상화 — 다른 모듈은 GPS/PTP 하드웨어를 몰라도 됨.
  • 시계 접근 없는 모듈 — PHC/PPS를 직접 못 읽는 프로세서는 받아야만 함.
  • 프레임 틱/에폭 배포 — 단순 시각이 아니라 슬롯 경계 정렬용 동기 스트로브일 수도.

GPU vRAN에선 이 중앙 배포가 사라지는 게 아니라 승격·표준화됩니다. 모두가 읽는 시스템시계는 phc2sys가 NIC PHC에 맞춰 규율한 단 하나의 소스 — 각 모듈이 자기 servo를 돌리는 게 아니라 중앙에서 규율된 값을 읽는 것입니다. 당신 모듈의 두 역할(① 단일 규율 소스 ② 배포)이 PHC(HW) + ptp4l/phc2sys(OS)로 흡수돼, 더 견고한 곳으로 옮겨갑니다.

⚠️ 단, 무엇을 뿌렸느냐가 갈림길
뿌린 것GPU vRAN에서
시각 값 (time of day, 거친 시간)phc2sys + CLOCK_TAI로 깔끔히 대체 → 각자 읽기 OK
프레임 틱 / 슬롯 에폭 (동기 스트로브)"각자 시계 읽기"로 안 됨 → NIC HW 타임스탬프(RX) + Accurate Send Scheduling(TX) + SFN↔PHC 에폭 조정점으로 이전

다른 모듈은 시간을 어떻게 받나 (CPU 모듈 포함)

"그럼 다른 CPU 모듈도 NIC에 접근해 시간을 가져갈 수 있나?" — 네, 됩니다. 두 가지 방법으로. 핵심은 진실원이 NIC PHC 하나이고, 모두가 그걸 참조한다는 점입니다.

방법어떻게언제
① 간접 (권장·기본)phc2sys가 PHC↔시스템시계(CLOCK_TAI/REALTIME)를 정렬 → 모듈은 평소처럼 시스템시계만 읽으면 이미 PHC에 동기됨대부분의 CPU 모듈 (제어·로그·OAM)
② 직접/dev/ptpN을 열어 clock_gettime()(동적 POSIX 클럭) 또는 PTP ioctl로 PHC를 직접 읽음더 타이트한 정렬이 필요한 모듈
💡 핵심 — 모두가 NIC을 직접 찌를 필요는 없다

phc2sys가 PHC를 시스템시계에 흘려주므로, CPU 모듈들은 그냥 시스템시계(CLOCK_TAI)를 읽기만 해도 PHC에 동기된 시각을 얻습니다. 당신이 지금 "한 모듈이 시간을 계산해 뿌리던" 일을, 이제 phc2sys가 OS 차원에서 대신해 주는 셈이죠 (push → 공통 참조 pull). 단, 소프트웨어 클럭 읽기는 지터가 µs 수준이라 제어용엔 충분해도 데이터 평면 슬롯 타이밍엔 부적합 — 그건 4절의 HW 타임스탬프를 씁니다. 또한 NIC이 여러 개면 PHC도 여러 개이니, 하나를 마스터로 정하고 나머지를 규율해 시간 도메인을 하나로 유지해야 합니다.

왜 NIC 직접 말고 Linux 시스템 시계인가

"NIC이 타임스탬프도 하는데 왜 굳이 시스템 시계를 가져왔나?" — 핵심은 "이벤트에 시각 찍기(timestamping)"와 "지금 몇 시? 질의(querying)"는 다른 일이라는 것입니다. NIC이 잘하는 건 전자고, 모듈들이 보통 필요한 건 후자입니다.

NIC 하드웨어 타임스탬프Linux 시스템 시계
하는 일이벤트에 시각 찍기 (패킷 도착/송신 순간)"지금 몇 시?" 질의 응답
적합데이터 평면, 패킷 단위제어·로그·스케줄·일반

시스템 시계를 쓴 합당한 이유들:

  • 읽기가 압도적으로 싸다 — 시스템 시계는 vDSO로 syscall 없이 수 ns(TSC 읽기). PHC 직접 읽기는 PCIe 왕복 → 수 µs. 시간을 자주 물으면 수백~수천 배 차이.
  • 표준 API — clock_gettime(CLOCK_TAI) 한 줄. /dev/ptp + ioctl은 하드웨어 특정적이고 복잡.
  • 시스템 전체가 하나의 타임베이스 — 로그·스케줄러·timerfd·파일시스템·OAM이 다 시스템 시계 기준. 일부만 PHC를 직접 읽으면 두 타임베이스가 생겨 어긋남.
  • 하드웨어 추상화·이식성 — NIC을 바꿔도 API 동일.
  • phc2sys가 이미 다리 — 시스템 시계 = PHC 품질(servo 오차 내). 굳이 PHC 직접 안 읽어도 PHC급 시간을 싸게 얻음.
✅ 그래서 — 옳은 선택이고, GPU vRAN에서도 유지

NIC 타임스탬프는 이벤트(패킷)에 시각 찍기용, 시스템 시계는 "지금 몇 시?" 질의용 — 용도가 다릅니다. GPU vRAN에서 바뀌는 건 딱 하나: 데이터 평면 패킷 타이밍만 NIC 하드웨어 타임스탬프로 넘기고, 제어·일반 시간 질의는 여전히 (phc2sys로 규율된) 시스템 시계를 씁니다. "PHC 있으니 다 직접 읽자"가 아니라 — 자주·싸게 묻는 시간은 시스템 시계, 정밀한 이벤트 스탬프는 NIC입니다.

6. 결정적 포인트 — GPU는 절대 시각을 안 본다

GPU는 PTP에 동기된 실시간 시계가 없고, 필요도 없습니다. 역할이 분리되기 때문입니다:

  • GPU — 슬롯/심볼 인덱스 공간에서 작업. "슬롯 N의 IQ를 계산하라."
  • NIC — 절대 시각 매핑 담당. "슬롯 N은 PHC 기준 몇 시에 송신/수신." (Accurate Send Scheduling)
  GPU 도메인 (인덱스)          ┃ 다리 ┃        NIC 도메인 (절대시각)
 ─────────────────────────────╂──────╂──────────────────────────────
  "슬롯 N 심볼 M 처리"   ◀────  PHC ↔ SFN 앵커링  ────▶  PHC 절대시각(TAI)
  결정론: 윈도우 마감 준수      ┃      ┃        HW 타임스탬프 / Send Scheduling

그래서 당신이 지금 SW로 모듈마다 슬롯 시각을 뿌리던 일을, 데이터 평면에선 NIC 하드웨어가 패킷 단위로 대신합니다. GPU는 절대 시각을 몰라도 슬롯 인덱스만으로 정확히 동작합니다.

다른 모듈이 슬롯/심볼 얻기 — 유도 vs 배포

"다른 모듈들이 슬롯/심볼 번호가 필요하면?" — 핵심은 슬롯/심볼은 "배포해야 할 상태"가 아니라 "계산해서 얻는 값"이라는 것입니다. 시간 배포 때와 똑같은 원리예요. 

슬롯 번호 = f( 현재 시간,  SFN 에폭(SFN 0의 절대시각),  numerology(SCS→슬롯 길이) )

시간 + 고정 설정 둘만 있으면 누구든 계산할 수 있고, 모두가 같은 시계 + 같은 에폭·numerology를 쓰면 각자 계산해도 다 같은 답이 나옵니다. 슬롯 번호를 매 슬롯 뿌릴 필요가 없습니다.

모듈이 얻는 3가지 경로

상황방법
"이 데이터가 어느 슬롯?"패킷 헤더에서 읽기 — eCPRI 헤더의 frameId/slotId/startSymbolId (RX 경로)
"지금 몇 번 슬롯?"로컬 계산 — slot = floor((now − T0) / slot_len) (modulo). 시스템 시계 읽고 산술
"슬롯 경계에 깨워줘"PHC 파생 타이머(timerfd/HW 타이머) 또는 슬롯 틱

공유할 건 슬롯 번호가 아니라 "에폭 앵커" 한 번

슬롯 번호는 안 뿌려도, SFN 에폭 앵커("SFN 0 = TAI 시각 T0")와 numerology는 공유해야 합니다. 단 이건 매 슬롯 바뀌는 상태가 아니라 초기화 때 한 번 정하는 설정/참조값입니다. 보통 MAC/스케줄러가 PTP에 맞춰 프레임 타이밍을 정렬하며 세웁니다. 즉 "프레임 틱/에폭"은 남기되, 슬롯 번호 자체를 매번 뿌리는 건 불필요합니다.

⚠️ 함정
  • 모든 모듈이 같은 에폭+numerology 써야 함 → 안 그러면 슬롯 번호 어긋남 (설정 일관성)
  • 시계가 PHC에 규율돼야 모두 같은 시간 → 같은 슬롯
  • wrap-around — SFN(0~1023)·프레임 내 슬롯 wrap → modulo 처리
✅ 정리 (+ GPU는 예외)

슬롯/심볼은 (시간 + 에폭 + numerology)에서 계산되는 값입니다 — 데이터의 슬롯은 패킷 헤더에서, 현재 슬롯은 공유 시계로 로컬 계산, 경계 트리거는 PHC 타이머로. 공유할 건 슬롯 번호가 아니라 에폭 앵커 한 번뿐. 단 GPU는 동기 시계가 없어 계산 대신 "슬롯 N" 인덱스를 넘겨받습니다.

7. 재설계 체크리스트

  1. 시간 진실원 재배치 — CPU 시스템 시계 → NIC PHC 기준. phc2sys로 PHC↔시스템시계 정렬은 유지(제어용).
  2. 슬롯 타이밍 배포 모듈 개조 (b 케이스) — SW 푸시 브로드캐스트 제거 → PHC 공통 앵커 + HW 타임스탬프 기반 풀 구조로.
  3. 슬롯↔PHC 앵커링 로직 — SFN/슬롯 경계가 PHC 절대시각 몇에 해당하는지 계산. T1a/Ta3/Ta4 윈도우가 여기서 파생.
  4. NIC/DPU 선택 — HW PTP 타임스탬핑(PHC), Boundary Clock, Accurate Send Scheduling 지원 (ConnectX-7/BlueField-3).
  5. 패킷 경로 — DPDK + GPUDirect, flow steering로 U/C/S 분류.
  6. 결정론 — GPU 파이프라인이 윈도우 마감 안에 끝나는지(tail latency), CUDA Graphs/persistent kernel.
  7. 제어 평면 유지 — OAM·로그·스케줄 결정용 SW 시간 배포는 그대로.
  8. 측정·검증 — TAE 측정, PTP 정확도(±ns), 윈도우 위반(late/early packet) 모니터링 (Calnex, VIAVI).
  9. 시스템 튜닝 — core isolation, NUMA(NIC·GPU 같은 노드), IRQ affinity, RT 커널.
✅ 이 페이지 정리

① vRAN 타이밍 = 망 시간(NIC PHC) ↔ 처리 시간(GPU 슬롯 인덱스) 두 도메인 정렬. ② PTP는 CPU(ptp4l/phc2sys)가 계속 돌리되 진실원은 NIC PHC. ③ "CPU에서 읽어 SW로 슬롯 타이밍 뿌리던" 구조는 NIC HW 타임스탬프 + Accurate Send Scheduling으로 대체 — 당신의 (b) 모듈이 1순위 개조 대상. ④ GPU는 절대 시각을 모르고 슬롯 인덱스로 일한다. 출발점은 NVIDIA/5t5g.
