eAxC ID 매핑

프론트홀로 들어오는 수십~수백 개의 IQ 스트림을 "어느 안테나·캐리어·레이어인지" 식별해 올바른 GPU 버퍼로 보내는 열쇠가 eAxC ID입니다. C/U-plane 분류보다 한 단계 더 세밀한, 스트림 단위 디멀티플렉싱을 다룹니다.

1. eAxC란

eAxC = extended Antenna-Carrier. O-RAN 프론트홀에서 하나의 논리적 IQ 스트림을 가리키는 식별자입니다. "어느 안테나(또는 레이어) × 어느 캐리어 × 어느 섹터"의 데이터인지를 한 숫자로 표현하죠.

  • massive MIMO는 안테나·레이어가 많아 스트림이 수십~수백 개. 이걸 구분 못 하면 어느 데이터가 어느 안테나 건지 알 수 없습니다.
  • eCPRI 헤더에 실립니다 — C-plane은 ecpriRtcid(Real-Time Control), U-plane은 ecpriPcid(IQ data) 필드에 같은 eAxC ID가 들어갑니다.
  • 즉 eAxC ID는 C-plane 제어 메시지와 그에 대응하는 U-plane IQ를 묶는 키이기도 합니다.

2. eAxC ID 구조 — 16비트, 4개 서브필드

eAxC ID는 16비트이고, 4개 서브필드로 나뉩니다. 각 필드의 비트 폭은 M-plane으로 설정(configurable)되며 합이 16비트입니다.

서브필드의미
DU_Port_IDDU 쪽 포트/처리 요소 식별
BandSector_ID밴드 & 섹터
CC_IDComponent Carrier ID — 어느 캐리어
RU_Port_IDRU 내 공간 스트림/안테나/레이어 식별
 
// 16비트 eAxC ID 예 (비트 폭은 설정에 따라 다름)
 ┌───────────┬──────────────┬────────┬────────────┐
 │ DU_Port   │ BandSector   │ CC_ID  │ RU_Port    │
 │  (2b)     │   (4b)       │  (2b)  │   (8b)     │   ← 합 16b
 └───────────┴──────────────┴────────┴────────────┘
   ↑ 어느 DU 포트  ↑ 섹터      ↑ 캐리어  ↑ 안테나/레이어
🔑 핵심

비트 할당이 고정이 아니라 배치(deployment)마다 설정됩니다. RU_Port에 비트를 많이 주면 더 많은 안테나/레이어를, CC_ID에 많이 주면 더 많은 캐리어를 표현할 수 있습니다. 이 설정을 DU와 RU가 M-plane으로 합의해야 서로 같은 해석을 합니다.

3. flow steering로 큐 분류

들어오는 수백 개 eAxC 스트림을 CPU가 일일이 분류하면 느립니다. NIC이 eAxC ID(또는 그 일부 비트)로 하드웨어 flow steering해 각 스트림을 알맞은 RX 큐로 보냅니다. 

// DPDK rte_flow: eAxC ID 비트 매칭 → 큐 지정 (개념)
패턴: eCPRI 헤더의 ecpriPcid == 특정 eAxC  →  액션: 큐 N으로
                                          →  (+ GPUDirect로 GPU 버퍼에 적재)
  • U-plane 스트림 → 각 eAxC별/그룹별 큐 → GPUDirect로 GPU 메모리 직접 적재
  • C-plane 스트림 → CPU 큐 → 파싱해서 처리 파라미터 셋업 (C가 U를 구성)
  • 큐를 여러 코어/스트림에 분산해 부하를 나눔 (RSS 유사)

4. GPU 버퍼 레이아웃 매핑

flow steering이 "어느 큐"까지 정해주면, 그다음은 "GPU 메모리 어느 위치"로의 매핑입니다. GPU 신호처리가 인덱스로 접근하도록 버퍼를 다차원으로 조직합니다. 

// 수신 IQ 버퍼의 논리적 인덱스
buffer[ eAxC ][ slot ][ symbol ][ PRB/RE ]
         │       │       │         └ 주파수 자원
         │       │       └ OFDM 심볼
         │       └ 슬롯 번호
         └ 안테나/레이어 (스트림)

패킷이 도착하면 eAxC ID(어느 안테나) + 헤더의 slot/symbol/PRB로 위 버퍼의 정확한 offset을 계산해 IQ를 써넣습니다 (RX 수신 정렬의 안테나 차원 버전).

💡 레이아웃이 성능을 좌우

채널 추정·MIMO 검출은 특정 RE에 대해 모든 안테나(eAxC)를 한꺼번에 봐야 합니다. 그래서 "같은 RE의 여러 eAxC가 메모리에서 인접"하도록 레이아웃을 짜면 GPU가 coalesced 접근으로 빠르게 읽습니다. eAxC를 가장 안쪽 차원에 두느냐 바깥에 두느냐가 커널 성능에 직접 영향을 줍니다.

5. massive MIMO와 Category A/B

eAxC가 물리 안테나를 뜻하는지 레이어를 뜻하는지는 O-RAN split category에 따라 다릅니다 — 빔포밍/프리코딩을 누가 하느냐의 문제입니다.

Category빔포밍/프리코딩 위치eAxC가 가리키는 것
Category AO-DU (DU가 프리코딩)대체로 안테나 포트/공간 스트림 (DU가 안테나별 데이터 전송)
Category BO-RU (RU가 프리코딩)대체로 레이어 (DU는 레이어별 + 빔포밍 정보 전송)

이게 중요한 이유 — Cat B는 RU가 빔포밍하므로 프론트홀에 흐르는 eAxC 수가 레이어 수(보통 안테나보다 적음)라 대역폭이 절감됩니다. 반면 Cat A는 안테나별로 다 보내 eAxC가 많아지고 대역폭 부담이 큽니다. 어느 쪽이냐에 따라 GPU 버퍼 차원·flow steering 규칙 수·대역폭 설계가 달라집니다.

✅ 이 페이지 정리

① eAxC ID = "어느 안테나/레이어 × 캐리어 × 섹터"를 가리키는 16비트 키(4개 서브필드, 비트폭 설정 가능). ② NIC flow steering이 eAxC로 큐 분류 → GPUDirect로 GPU 적재. ③ GPU 버퍼는 [eAxC][slot][symbol][PRB]로 조직하고, 레이아웃이 coalescing 성능을 좌우. ④ eAxC가 안테나냐 레이어냐는 Category A/B(빔포밍 위치)에 달려 있고, 이게 대역폭·버퍼 설계를 바꾼다.
