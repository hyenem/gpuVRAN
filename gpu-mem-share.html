GPU 메모리 공유 & 코어 협력

"GPU 코어들끼리 메모리를 공유하나? CP가 설정한 걸 다른 코어가 UP 받았을 때 시간 지연 없이 처리할 수 있나?" — 핵심은, GPU의 메모리 모델이 CPU와 근본적으로 달라서 코어 간 핸드오프 문제 자체가 거의 사라진다는 점입니다.

1. GPU 메모리 공유 계층 — 어디까지 공유되나

메모리공유 범위
레지스터스레드 1개 (private)
Shared memory블록 안 스레드끼리 (on-chip, 빠름)
L1 캐시SM 1개
L2 캐시모든 SM 공유
Global memory (VRAM)모든 스레드·SM·블록 공유 ✅

즉 global memory에 올려둔 데이터는 어느 코어(SM)에서든 다 보입니다. CP가 만든 설정(어느 PRB·빔·압축)을 global memory에 써두면, U-plane을 처리하는 어떤 스레드든 그냥 읽습니다 — "다른 코어로 넘겨주는" 복사가 필요 없습니다. (계층 자체는 Part 1 메모리 계층과 동일하며, 여기선 "공유 범위" 관점으로 봅니다.)

2. CPU와의 결정적 차이

당신의 현재 CPU 설계에선 CP 코어 → UP 코어로 설정이 가려면 캐시 일관성(coherency) / 락 / 메시지 패싱을 거칩니다. 캐시라인 바운싱, false sharing, 락 경합 같은 지연이 생기죠.

CPUGPU
코어 간 데이터사적 캐시 → 일관성 프로토콜로 동기화공유 global memory를 같이 읽음
전달 비용캐시라인 바운싱·락·false sharing공유 메모리 읽기 (전달 개념 약함)
멘탈 모델"누가 누구에게 넘겨준다""다 같은 메모리를 본다"

GPU는 코어마다 사적 캐시를 동기화하는 모델이 아니라, 공유 global memory를 수천 스레드가 같이 읽는 모델입니다. 설정을 한 번 써두면 모두가 봅니다. 그래서 "코어 간 전달 지연"이라는 개념이 약해집니다.

3. 그래서 "시간 지연 없이?" — 진짜 변수는 따로 있다

핸드오프가 아니라 생산자→소비자 순서(ordering)가 진짜 고려사항입니다:

CP 파싱 → 설정을 global memory에 기록  ──(이게 먼저 끝나야)──→  U-plane 커널이 읽음

여기서 두 가지가 이걸 "지연 없이"로 만들어 줍니다:

  1. C-plane이 U-plane보다 먼저 도착 (T1a 리드타임) → 설정은 U-plane 처리 시작 전에 이미 준비됨. 의존성이 파이프라인으로 숨겨져 크리티컬 패스에 지연을 안 더함.
  2. 커널 launch가 메모리 배리어 → 이전 단계(CPU나 직전 커널)가 쓴 설정은 다음 커널이 launch될 때 가시성이 보장됨. 그래서 U-plane 커널은 별도 동기화 없이 그냥 읽으면 됨.
💡 핵심

GPU에선 CP 설정→UP 처리가 코어 간 전달이 아니라 공유 메모리 읽기입니다. CP가 U보다 먼저 와서(T1a) 설정이 미리 준비되고, 커널 launch가 가시성을 보장하므로 — 제대로 설계하면 크리티컬 패스엔 추가 지연이 없습니다.

3.5 CP가 제때 안 끝나면 — 크리티컬 패스 게이트

위 전제("CP가 먼저 와서 준비된다")가 깨지는 경우 — CP가 같은 블럭의 무거운 작업에 묶여 UP 시작 전에 안 끝나면? 이건 크리티컬 패스 의존성 위반입니다. CP가 UP를 게이트(gate)하니까요.

⚠️ CP는 원래 늦으면 안 되는 놈

CP는 작은 제어 메시지라 파싱이 빠릅니다. 그게 늦었다면 연산량이 아니라 스케줄링/자원 경합 문제 — "CP가 느린 작업 뒤에 줄 서 있다"는 설계 냄새(design smell)입니다. CP는 작지만 가장 급한 일이에요.

예방 — CP를 느린 것과 떼고 우선순위를 준다

  1. CP를 무거운 UP 작업과 분리 — CP 파싱을 무거운 GPU 커널/블럭에 끼워넣지 말 것. CP는 CPU(전용 경로), UP는 GPU. "같은 블럭"이라는 것 자체가 고칠 지점.
  2. 높은 우선순위·전용 자원 — CP는 작으니 전용 코어에서 도착 즉시 처리. 벌크 뒤에 큐잉 금지.
  3. CP 자체의 더 타이트한 데드라인 — CP는 UP보다 먼저 끝나야 하니 사실상 더 이른 마감(DL이면 T1a_cp 윈도우). 이 안에 들도록 예산 잡고 최악 지연 측정.
  4. 파이프라인 깊이 늘리기 — 슬롯 N의 CP를 더 앞당겨 처리해 리드타임 여유 확보.

원칙: CP의 worst-case 지연 < T1a 리드타임 이 보장돼야 UP 시작 시점에 설정이 항상 준비됩니다.

그래도 늦으면 (실패 처리)

늦은 UP 패킷과 똑같이 — 기다리면 죽습니다:

선택현실성
슬롯 드롭 (슬롯 단위 erasure)✅ 가장 현실적 — 슬롯 처리 포기, fault 로깅, HARQ 재전송에 맡김
기본/이전 슬롯 설정 재사용⚠️ 보통 위험 — 설정은 슬롯마다 다름(빔·PRB 변경), 잘못된 처리 유발
무한정 대기❌ HARQ 마감 깨짐 → 더 큰 실패
✅ 핵심

이건 정상 동작이 아니라 예외(fault)여야 합니다. 자주 일어나면 시스템이 under-provisioned(자원 부족)인 것이고, 해법은 "기다리기"가 아니라 CP 경로를 더 빠르게·분리·우선순위화하는 것입니다. CP의 worst-case 지연 < 리드타임이 보장되도록 설계·측정하는 게 본질.

4. 챙겨야 할 디테일

  • CP가 CPU에서 파싱되면 설정이 CPU→GPU 경계를 한 번 넘습니다(작은 비용). 단 이건 리드타임 동안 미리 하니 크리티컬 패스 밖. CP 파싱도 GPU(cuMAC류)에서 하면 아예 global memory 안에서 끝나 더 깔끔.
  • 설정은 모든 스레드가 같이 읽으므로 → constant memory나 read-only 캐시에 두면 브로드캐스트 읽기로 최적화됩니다 (수천 스레드가 같은 값 읽기에 이상적).
  • 주의할 케이스 — 같은 커널 실행 중에 한 블록이 만든 걸 다른 블록이 읽어야 한다면, 그땐 __threadfence()나 cooperative groups 같은 명시적 동기화가 필요하고 비용이 듭니다. 하지만 CP/UP는 보통 "설정 먼저 완성 → 그다음 커널"이라 이 경우가 아닙니다.
✅ 한 줄 정리

GPU는 global memory를 모든 코어가 공유하므로 CP 설정→UP 처리는 코어 간 전달이 아니라 공유 메모리 읽기입니다. CP가 U보다 먼저 와서(T1a) 설정이 미리 준비되고 커널 launch가 가시성을 보장하므로 — 잘 설계하면 추가 지연이 없습니다. CPU의 캐시 일관성 핸드오프 걱정을 GPU에선 안 해도 됩니다.
