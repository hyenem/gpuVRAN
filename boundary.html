경계 설계: 버퍼 수명 & 작업 분할

CPU↔GPU 경계는 이론이 아니라 실전 엔지니어링이 부딪치는 곳입니다. 두 가지 현실 문제 — "버퍼(mbuf)를 언제 free하나?"와 "CPU가 일부 처리하면 더 빠르지 않나?"를 정리합니다.

1. mbuf는 언제 free하나

흔한 레거시 설계 — DPDK mbuf를 여러 코어가 공유하고, "몇 슬롯 뒤 한꺼번에 free". 이건 "그때쯤이면 처리가 끝났겠지"라는 시간 가정에 기댑니다. GPU로 가면 이 가정이 깨집니다.

⚠️ 왜 깨지나

GPU는 타임라인이 분리돼 있어 CPU가 "GPU가 언제 끝나는지"를 모릅니다. 게다가 GPUDirect로 IQ가 GPU 메모리에 있으니, GPU가 다 쓸 때까지 mbuf를 살려둬야 합니다. 시간으로 free하면:

  • 너무 일찍 free → GPU가 아직 읽는 메모리 회수 = use-after-free / 데이터 손상
  • 너무 늦게 free → mempool 고갈 → 패킷 드롭

완료(completion) 기반 free로 전환

핵심 — 시간 기반 free를 버리고, GPU가 "끝났다"고 알려주게 만듭니다.

메커니즘방법
CUDA event소비 커널 뒤 cudaEventRecord → CPU 정리 스레드가 cudaEventQuery 폴링 → free
Stream callbackcudaLaunchHostFunc로 스트림이 그 지점 도달 시 호스트 함수 실행 → free 트리거
완료 플래그/세마포어GPU가 메모리에 "슬롯 N 완료" 기록 → CPU가 폴링

여러 코어 공유 → 참조 카운트(refcnt)

mbuf의 rte_mbuf_refcnt를 씁니다. 각 사용자(코어들 + GPU)가 ref를 잡고 0이 되면 free. 단 GPU는 직접 rte_pktmbuf_free를 못 부르므로, GPU 완료 신호를 받은 호스트 프록시 스레드가 GPU 몫의 ref를 대신 내려줍니다. 모든 CPU 사용자 + GPU가 release해야 free됩니다.

구조는 유지, 트리거만 교체

"슬롯별로 모아 batch free" 구조는 그대로 둬도 됩니다. 트리거만 바꾸세요:

[기존] 슬롯 N의 mbuf 리스트 → "벽시계로 N슬롯 뒤"  → 한꺼번에 free   ❌ GPU 지터에 취약
[변경] 슬롯 N의 mbuf 리스트 → "GPU 완료 이벤트(N)" → 한꺼번에 free   ✅ + 안전 타임아웃 백스톱

완료 신호가 권위(authoritative)이고, 시간은 백스톱일 뿐입니다.

🛠️ 관련 도구
  • mbuf external buffer (rte_pktmbuf_attach_extbuf) — 페이로드를 GPU 메모리에 두고 free 콜백 등록
  • DPDK gpudev(rte_gpudev) + DOCA GPUNetIO — GPU 메모리 관리 + GPU 주도 패킷 I/O·세마포어. 정확히 이 수명 문제를 위해 만들어진 프레임워크
  • mempool 사이징 — 파이프라인 깊이(in-flight 슬롯 수)×슬롯당 버퍼×여유. GPU가 지연을 더하니 in-flight가 늘어 풀을 더 크게

2. CPU가 일부 처리하면 더 빠를까

직관은 타당합니다 — CPU가 유리한 구간이 분명히 있습니다. 다만 "packet 사이즈로 나누기"는 L1 구조상 깔끔히 안 맞아, 나누는 축을 바꿔야 합니다.

CPU가 이기는 구간은 진짜 있다

GPU는 크고·규칙적·병렬 작업에, CPU는 작고·지연민감·분기 많은 작업에 강합니다. 크로스오버가 존재합니다:

  • 저부하 / 적은 PRB — GPU 고정 오버헤드(launch·전송)가 안 빠짐 → CPU가 더 빠를 수 있음
  • 제어 평면 / 불규칙 — C-plane, 스케줄링 → CPU
  • 아주 작은 지연민감 작업 — CPU

그런데 "packet 사이즈로 split"이 어려운 이유

vRAN L1 단계(FFT·채널추정·MIMO·LDPC)는 슬롯/심볼 전체에 걸쳐 결합돼 있습니다:

  • FFT는 한 심볼의 모든 서브캐리어가 있어야 함
  • MIMO는 여러 안테나를 묶음
  • LDPC는 코드블록 단위

그래서 "작은 패킷은 CPU, 큰 패킷은 GPU"로 같은 처리 단계를 쪼개는 건 잘 안 됩니다. 작은 패킷도 결국 같은 심볼의 일부라, 따로 떼면 그 심볼 처리가 불완전해집니다.

대신 나누는 진짜 축

분할 축예
기능별 (functional)FEC만 다른 엔진(=lookaside), 나머지는 GPU
셀/캐리어/유저 그룹별셀 A는 GPU, 셀 B는 CPU
평면별C-plane은 CPU, U-plane은 GPU
부하 적응형저부하 슬롯 → CPU, 고부하 → GPU

C/U-plane 분류 — 가장 자연스러운 분할

위 표의 "평면별" 축을 자세히 봅니다. 이게 packet 사이즈 분할과 달리 구조에 안 거슬리는 좋은 축인 이유 — C-plane과 U-plane은 애초에 다른 데이터라서입니다.

평면정체성격 → 어디로
C-plane (제어)"이 슬롯에 어느 PRB·어떤 빔·어떤 압축으로 처리하라"는 스케줄/섹션 정보작고·분기 많고·제어 로직 → CPU
U-plane (사용자)실제 IQ 샘플 (대용량)크고·규칙적·병렬 → GPU
📐 용어 주의

프론트홀엔 4평면(C/U/S/M)이 있고, 여기 C/U는 프론트홀 평면입니다. 상위의 CU-CP / CU-UP 분리(5G에서 CU를 제어/사용자 노드로 나눔)와는 다른 레벨이에요. 우리 맥락(DU/L1)에선 프론트홀 C/U-plane을 말합니다.

핵심 — C-plane이 U-plane을 어떻게 처리할지 알려준다

C-plane 먼저 도착 → 파싱(CPU): "슬롯 N, 심볼 M, PRB 0~50, 빔 ID 3, BFP 압축"
                              ↓ 이 정보로 U-plane 처리를 구성(configure)
U-plane 도착 → GPUDirect로 GPU → C-plane이 지정한 대로 FFT·채널추정·MIMO·LDPC
  • C-plane: 작은 제어 메시지, 분기·룩업 많음, U-plane보다 먼저(T1a 윈도우) 도착 → CPU가 파싱해 처리 파라미터 셋업
  • U-plane: 대량 IQ, 단순·병렬 → GPU가 C-plane이 정해준 설정대로 대량 처리

어떻게 분류하나 — NIC flow steering

  • NIC이 eCPRI 메시지 타입 / eAxC ID로 C-plane·U-plane을 다른 큐로 분류 (하드웨어 flow steering)
  • C-plane 큐 → CPU 파싱 / U-plane 큐 → GPUDirect로 GPU 직접 적재
✅ 왜 "좋은" 분할인가
  • 의미(semantic)가 다른 데이터 — 제어 vs 데이터, 처리 파이프라인 자체가 다름
  • 병합 문제 없음 — 합치는 게 아니라 C가 U를 구성하는 관계
  • 각 칩 강점에 정확히 매칭 — 분기 제어는 CPU, 대량 병렬은 GPU

그래서 NVIDIA Aerial 같은 inline 구조도 "다 GPU"가 아니라 — C-plane 파싱·MAC 스케줄링은 CPU(또는 cuMAC), U-plane 신호처리는 GPU라는 평면 분리가 기본으로 깔려 있습니다.

숨은 비용 — 이게 결정적

  1. 데이터 지역성 — 패킷이 이미 GPUDirect로 GPU 메모리에 있는데 "작으니 CPU로" 도로 끌어오면 전송 비용이 이득을 까먹음. 데이터가 있는 곳에서 처리가 원칙
  2. 병합·동기 오버헤드 — 한 슬롯을 CPU+GPU로 쪼개면 결과를 합치고 타임라인 맞춰야 함 → 지터 추가
  3. 결정론 — 하이브리드는 평균은 빨라도 꼬리(tail)가 튀어 실시간 마감을 깰 수 있음. 실시간에선 균일한 경로가 종종 더 안전
🔗 이건 inline vs lookaside 논쟁의 미세판

NVIDIA(inline)는 "다 GPU에서 해서 split 오버헤드·지터 없애자", Intel(lookaside)은 "FEC만 떼자". 당신의 "CPU가 일부 처리" 질문은 이 논쟁을 더 잘게 가져온 것입니다.

✅ 실전 가이드
  1. 슬롯당 병렬 작업량이 launch+전송을 amortize할 만큼 클 때만 GPU로
  2. 제어·작은·분기 작업은 CPU에
  3. 나눌 거면 packet 사이즈가 아니라 셀/캐리어 단위로
  4. 무엇보다 크로스오버를 직접 측정해서 결정 (워크로드·하드웨어마다 다름)
