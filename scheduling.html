④ 스케줄링

블록이 SM에 배정된 뒤, 그 안에서 warp가 어떻게 골라 실행되는가 — 그리고 여러 커널이 GPU를 두고 어떻게 경쟁하는가. 성능과 응답성의 핵심입니다.

4.1 Warp 스케줄링 — latency hiding

SM의 warp 스케줄러(보통 4개/SM)는 매 사이클 "실행 준비된(ready) warp"를 골라 명령을 냅니다. 한 warp가 global memory를 기다리며 멈추면(수백 사이클), 즉시 다른 warp로 0-오버헤드 전환합니다. 

warp A: 메모리 대기 ──┐
warp B: 실행          │  A가 멈춘 동안 B·C·D 실행 → ALU 안 놀림
warp C: 실행          │  (= latency hiding)
warp D: 실행 ─────────┘

CPU는 캐시로 지연을 줄이고, GPU는 많은 warp로 지연을 가립니다. 그래서 SM에 ready warp가 충분해야 ALU가 꽉 찹니다 — 이게 다음의 occupancy 이야기입니다.

4.2 Occupancy 튜닝

①에서 본 occupancy를 실제로 어떻게 올리나:

제약올리는 법
레지스터/스레드 과다변수 줄이기, __launch_bounds__로 레지스터 상한 힌트
shared memory/블록 과다타일 크기·버퍼 축소
블록 크기 부적절128~256 스레드 등으로 조정 (occupancy calculator 활용)
📌 occupancy가 전부는 아니다

occupancy를 높이면 보통 좋지만, 100%가 항상 최적은 아닙니다. 레지스터를 늘려(occupancy↓) 스레드당 일을 더 시키는 게 빠를 때도 있어요(ILP). "occupancy는 latency hiding에 충분할 만큼만" 확보하고, 실제 성능은 프로파일러로 확인하세요.

4.3 스트림 우선순위

여러 스트림이 동시에 일할 때, 급한 작업을 먼저 실행시키고 싶다면 우선순위 스트림을 씁니다. 자원이 비면 우선순위 높은 스트림의 블록이 먼저 SM에 배정됩니다. 

int lo, hi;
cudaDeviceGetStreamPriorityRange(&lo, &hi);   // hi가 더 높은 우선순위(작은 값)
cudaStream_t urgent;
cudaStreamCreateWithPriority(&urgent, cudaStreamNonBlocking, hi);

4.4 선점(preemption)이 약하다

여기가 GPU의 중요한 한계입니다. 블록은 SM 자원을 차지한 채 끝까지 실행(run-to-completion)합니다. 거대한 커널의 블록들이 모든 SM을 점유하면, 급한 커널의 블록은 SM 자원이 빌 때까지 대기해요 (head-of-line blocking).

CPUGPU
선점강함 — 급한 스레드가 즉시 끼어듦약함 — 블록은 보통 끝까지 실행
우선순위 효과실행 중인 것도 뺏음주로 "다음 배정"에만 영향

(Pascal+ 부터 명령 단위 부분 선점이 있지만 거칠고 비쌈.) 그래서 응답성이 필요하면:

  • 커널을 작게/유계로 — 블록이 빨리 끝나 SM 자원이 자주 풀림
  • 스트림 우선순위 — 자원 빌 때 급한 블록부터
  • oversubscribe 금지 — GPU에 처리량 넘게 일을 안 쌓기

4.5 MIG · MPS — 자원 분리

여러 워크로드가 한 GPU를 공유할 때, 서로 간섭을 막는 두 방법:

MPS (Multi-Process Service)MIG (Multi-Instance GPU)
방식여러 프로세스의 커널을 한 컨텍스트로 합쳐 동시 실행GPU를 물리적으로 분할(SM·메모리 격리)
격리약함 (성능 간섭 가능)강함 (하드웨어 격리)
용도작은 커널 여러 개의 활용률↑QoS·멀티테넌시 보장
지원대부분 GPUA100/H100 등 데이터센터 GPU
✅ ④ 정리

SM은 ready warp로 0-오버헤드 전환해 지연을 가립니다(occupancy가 열쇠). 블록은 run-to-completion이라 선점이 약하니, 응답성은 작은 커널·스트림 우선순위·MIG/MPS로 확보합니다. 반복 워크로드의 launch 비용은 다음 장(⑤ Graphs)에서 없앱니다.
