③ CUDA 동작 방식 — 실행 모델

"kernel<<<...>>>()를 호출하면 실제로 무슨 일이 벌어지나?" — host에서 명령이 GPU로 흘러가 블록이 SM에 배정되기까지의 전 과정을 따라갑니다.

3.1 커널 launch의 실체

kernel<<<blocks, threads>>>() 한 줄이 실행되면 내부에서 이런 일이 일어납니다: 

① CPU(호스트): 런타임/드라이버에 "이 커널을 이 구성으로 실행" 요청 작성
② 드라이버:   명령을 GPU의 하드웨어 큐에 enqueue (이 작업 자체가 ~µs 오버헤드)
③ CPU:        기다리지 않고 다음 줄로 진행 (비동기!)
④ GPU:        큐에서 커널을 꺼내 grid를 펼침
              → GigaThread 엔진이 블록들을 SM들에 분배
⑤ 각 SM:      배정된 블록의 warp를 스케줄해 실행
⚠️ 커널 실행은 비동기다

CPU는 GPU 완료를 기다리지 않습니다 — enqueue만 하고 다음 줄로 갑니다. 결과가 필요하면 cudaMemcpy(자동 동기) 또는 cudaDeviceSynchronize()로 기다려야 합니다. 이 비동기성이 성능의 무기(overlap)이자 버그의 원천(동기화 누락)입니다.

그리고 ②의 launch 오버헤드(~µs)가 작은 커널을 많이 띄울 때 병목이 됩니다 — 이걸 없애는 게 ⑤ CUDA Graphs입니다.

3.2 비동기 · 스트림

CUDA 스트림은 GPU 작업의 "작업 큐"입니다. 같은 스트림 안의 작업은 순서대로, 다른 스트림끼리는 병렬로 실행됩니다. 이를 이용해 "데이터 전송"과 "연산"을 겹쳐(overlap) 숨깁니다. 

cudaStream_t s1, s2;
cudaStreamCreate(&s1); cudaStreamCreate(&s2);

// 청크 0은 s1, 청크 1은 s2 → 전송과 연산이 겹쳐 돌아감
cudaMemcpyAsync(dA0, hA0, sz, H2D, s1);
kernel<<<b,t,0,s1>>>(dA0);
cudaMemcpyAsync(dA1, hA1, sz, H2D, s2);
kernel<<<b,t,0,s2>>>(dA1);
// overlap 효과 (개념)
스트림1:  [복사0][커널0]
스트림2:        [복사1][커널1]   ← 복사1이 커널0과 겹침 → 총 시간↓

비동기 복사를 하려면 호스트 메모리가 pinned여야 합니다.

3.3 이벤트 · 동기화

스트림 사이 조율과 시간 측정엔 이벤트(event)를 씁니다.

  • 시간 측정 — cudaEventRecord 두 개 사이의 GPU 시간 측정(cudaEventElapsedTime). CPU 타이머보다 정확.
  • 스트림 간 의존성 — cudaStreamWaitEvent로 "스트림 B는 스트림 A의 이 지점까지 기다려라".
  • 전체 동기화 — cudaDeviceSynchronize()(모든 작업), cudaStreamSynchronize(s)(한 스트림).
cudaEvent_t start, stop;
cudaEventCreate(&start); cudaEventCreate(&stop);
cudaEventRecord(start);
kernel<<<b,t>>>();
cudaEventRecord(stop);
cudaEventSynchronize(stop);
float ms; cudaEventElapsedTime(&ms, start, stop);

3.4 블록 → SM 배정

grid가 펼쳐지면 GigaThread 엔진(블록 스케줄러)이 블록들을 SM에 분배합니다. 규칙:

  • 블록은 한 SM에만 배정 (절대 SM 사이로 쪼개지지 않음).
  • SM 하나는 여러 블록을 동시 거주(resident) — 자원(레지스터·shared·warp 슬롯)이 허락하는 만큼.
  • 블록이 끝나 자원이 풀리면 대기 중인 다음 블록이 그 SM에 올라감.
Grid: [B0][B1][B2][B3][B4][B5][B6][B7]...   (블록이 많음)
         │   │   │   │
        SM0 SM1 SM0 SM1   ← 자원 되는 대로 배정, 끝나면 다음 블록
🧠 함의

블록은 독립적이어야 합니다 — 어느 SM에, 어떤 순서로 배정될지 보장이 없으니까요. 그래서 블록 간 직접 동기화가 (커널 안에선) 안 되고, 블록끼리 협력하려면 커널을 나누거나 grid sync(cooperative groups)를 써야 합니다. 이 배정·실행이 실제로 어떻게 스케줄되는지는 ④ 스케줄링에서 이어집니다.

✅ ③ 정리

커널 launch는 비동기 enqueue(~µs 오버헤드) → GPU가 grid를 펼침 → GigaThread가 블록을 SM에 분배 → SM이 warp를 실행. 스트림으로 작업을 겹치고, 이벤트로 조율·측정합니다.
